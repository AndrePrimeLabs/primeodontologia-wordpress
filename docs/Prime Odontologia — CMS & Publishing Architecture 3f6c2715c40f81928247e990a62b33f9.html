Status
Done

Overview

This document describes the content publishing pipeline for Prime Odontologia (primeodontologia.com.br), which uses Notion as a headless CMS bridged to a WordPress.com production site via a custom daemon running on a Hostinger VPS.

Components

1. Notion CMS Database

  • Role: Editorial layer — all content is written, reviewed, and approved here
  • Managed by: Verum Labs / Prime Labs content team
  • Recommended fields: Title, Status, Slug, Category, Publish Date, WordPress Post ID, Author

2. Hostinger VPS Worker (82.29.56.236)

  • Role: Bridge between Notion and WordPress
  • Daemon: prime-notion-bridge
  • Responsibilities:
    • Polls or listens for Notion database changes (e.g., Status → "Ready to Publish")
    • Transforms Notion page content (blocks) into WordPress-compatible HTML/Gutenberg blocks
    • Pushes content to WordPress via the WordPress.com REST API
    • Authenticates using App Passwords (per-user, revocable credentials)
    • Updates the Notion record with the resulting WordPress Post ID and published URL

3. WordPress.com Production Site

  • URL: primeodontologia.com.br
  • Theme: prime-odontologia — a custom Block Theme built with WordPress Studio
  • Database: Managed MySQL (provided by WordPress.com infrastructure)
  • Role: Public-facing website; receives and displays content published by the bridge daemon

Content Publishing Workflow

  1. Draft — Writer creates/edits content in the Notion CMS database
  1. Review — Editor reviews and approves the content in Notion
  1. Ready to Publish — Status updated to trigger the bridge daemon
  1. Bridge Sync — prime-notion-bridge detects the change, converts, and POSTs to WordPress REST API
  1. Live — Post appears on primeodontologia.com.br; Notion record updated with Post ID + URL

Security Notes

  • WordPress App Passwords should be scoped per service account and rotated periodically
  • The VPS IP (82.29.56.236) should be allowlisted where possible on WordPress.com
  • Notion integration token should be stored as an environment variable (never hardcoded)
  • VPS access should be restricted via SSH key authentication only
