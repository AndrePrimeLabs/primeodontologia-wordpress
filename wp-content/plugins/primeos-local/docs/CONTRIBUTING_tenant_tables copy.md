# PrimeOsHub — Adding a New Tenant-Scoped Table

Every module (Finances, Marketing, Operations, Sales, etc.) will eventually need
its own tables. Any table that stores per-business data — not shared reference
data — MUST follow this checklist before it ships, regardless of whether it
was written by Claude Code or generated by Lovable.

## 1. Required columns

- [ ] `id` — `uuid primary key default gen_random_uuid()`
- [ ] `tenant_id` — `uuid not null references tenants(id) on delete cascade`
- [ ] `created_at` — `timestamptz not null default now()`
- [ ] `updated_at` — `timestamptz not null default now()` (add an `updated_at`
      trigger if the table will be edited after creation)

## 2. Index

- [ ] `create index on <table>(tenant_id);` — every tenant-scoped table gets
      this, no exceptions. RLS policies filter on `tenant_id` on every query;
      without the index this becomes a full table scan as data grows.

## 3. Row Level Security

- [ ] `alter table <table> enable row level security;`
- [ ] At minimum a `select` policy using `is_tenant_member(tenant_id)`
- [ ] Write policies (`insert`/`update`/`delete`) using either
      `is_tenant_member` (any member can write) or `is_tenant_admin`
      (owners/admins only) — pick deliberately per table, don't default to
      the more permissive one out of convenience
- [ ] If the table has a foreign key into another tenant-scoped table (like
      `canvas_block_items` → `canvases`), add a trigger that derives
      `tenant_id` server-side from the parent instead of trusting the client
      — see `primeoshub_tenant_id_trigger.sql` for the pattern

## 4. PII / sensitive columns

- [ ] Any column holding patient data, financial account details, or other
      PII gets `pgcrypto` column-level encryption on top of RLS — RLS
      controls row access, encryption protects the column even from someone
      with legitimate row access (e.g. a data export)
- [ ] Flag these columns explicitly in the migration file's comments so a
      future reviewer doesn't miss them

## 5. Who writes it

- [ ] **Claude Code** writes the migration file if the table needs RLS
      policies, triggers, or touches tenancy/security logic (i.e. almost
      always, per this checklist)
- [ ] **Lovable** may generate simple additive changes (a new nullable column
      on an existing, already-compliant table) but should NOT be the one
      creating new tables — route that back to Claude Code first
- [ ] Migration files live in `supabase/migrations/`, numbered sequentially,
      committed to Git — never applied by hand through the Supabase dashboard

## 6. Before merging

- [ ] Test with two dummy tenants: confirm tenant A cannot read, write, or
      trigger a foreign-key insert into tenant B's rows
- [ ] Confirm the table appears correctly in Supabase Dashboard →
      Authentication → Policies with all four policy types you intended
